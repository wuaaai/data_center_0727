# Plan: Modularize & Reorder Pipeline (Build-DOCX-then-Chunk)

## Context

当前项目将 PDF/DOCX 转换为带分块标记（`***` / `<-split->`）的 DOCX。存在两个问题：

1. **代码结构不够模块化**：`text_chunker.py`（1580行）和 `fast_pdf_parser.py`（850行）过于庞大，功能混杂（文本清洗、TOC过滤、图片分析、分块标记插入等耦合在一起）。`fast_docx_parser.py` 直接从 `fast_pdf_parser.py` 导入内部函数，依赖不清晰。

2. **处理顺序不合理**：当前是 解析 → 分块 → 生成DOCX，分块逻辑深度嵌入在解析器中。需要改为：解析 → 生成干净DOCX → 分块（作为可插拔的后处理步骤）。分块策略应可通过配置/CLI一键替换。

目标：保持功能效果完全不变，重构代码结构，实现分块策略可插拔。

### Data Flow Change

**旧流程：**
```
minerU:  PDF → parse_pdf → content_list → chunk_content_list → TextChunks
         → chunks_to_paragraphs → paragraphs (WITH ***/<-split->) → build_docx
快路径:  PDF/DOCX → parse_*_fast → paragraphs (WITH ***/<-split->) → build_docx
```

**新流程：**
```
所有路径:
  解析 → 干净段落 (无标记, 有 style/level)
       → strategy.chunk() → 标记段落 (有 ***/<-split->)
       → build_docx → .docx
```

解析器只负责提取内容并标注样式/层级，不再插入分块标记。分块策略接收干净段落，返回带标记段落。

### ChunkingStrategy Interface

```python
class ChunkingStrategy(ABC):
    @property
    def name(self) -> str: ...
    
    def chunk(self, paragraphs: list[dict], context: ChunkContext) -> list[dict]:
        """输入干净段落，输出带 *** 和 <-split-> 标记的段落"""
```

内置策略：
- `"default"` — 当前所有分块逻辑（*** + <-split-> + token拆分 + 列表合并 + 空标题合并）
- `"none"` — 无分块，直接输出干净段落（用于生成纯DOCX）
- `"size_only"` — 仅按 token 上限拆分，不插入 *** 父块标记

通过 `config.CHUNKING_STRATEGY` 或 CLI `--chunking-strategy` 选择。

## Key Technical Details

- **干净段落格式**：`{"text": str, "style": "Title"|"Heading 1"|"Heading 2"|"Heading 3"|"Normal", "level": int, "image": optional dict}`。text 永远不含 `***` 或 `<-split->`。
- **分块标记由策略统一插入**：`***` 在 Heading 前，`<-split->` 在正文间。策略不关心段落来源（minerU/快PDF/快DOCX）。
- **消除代码重复**：`_estimate_tokens()` 和 `_split_long_para()` 在 text_chunker 和 fast_pdf_parser 各有一份实现，合并到 `chunking/text_utils.py`。
- **向后兼容**：所有旧 import 路径通过 shim 保持有效。`chunk_content_list()` 和 `chunks_to_paragraphs()` 作为兼容包装继续工作。
