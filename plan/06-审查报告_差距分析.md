## 二、设计冲突和不一致

### ⚠️ 冲突5: 路由前缀不一致

| 方案 | 路由前缀 | 来源 |
|------|---------|------|
| P0 计划 Task 7 | `/file_parse` (独立) | 04-05 合并方案 |
| 06 方案 | `/ragdata/file-parse/` | 06 方案自定 |

**现状:** 04-05 合并方案中 `file_parse` 是独立的一级路由，但 06 方案把它放到了 `/ragdata` 前缀下。

**影响:** 路由冲突/风格不一致。现有所有路由都在 `/ragdata/` 下，`file_parse` 要不要也在 `/ragdata/` 下需要统一决策。

**建议:** 统一放在 `/ragdata/` 下，与现有代码风格一致。

---

### ⚠️ 冲突6: 批量并发控制与现有线程池的关系不清

**现有关键代码** (`routes.py` 第 50 行):
```python
_doc_executor = ThreadPoolExecutor(max_workers=4, thread_name_prefix="doc-proc")
```
每个文件通过 `loop.run_in_executor(_doc_executor, _process_document_background, ...)` 提交。

**06 方案新增:**
```python
MAX_CONCURRENT_BATCH = 6
self._semaphore = threading.Semaphore(MAX_CONCURRENT_BATCH)
```

**问题:** 信号量控制的是"同时提交到线程池的数量"还是"实际并发处理的数量"？如果线程池只有 4 workers，信号量设为 6 毫无意义——最多只有 4 个在真正执行。而且 `_process_document_background` 内部还会通过 HTTP 调用 MinerU 服务 (MinerU 自己也有并发限制)，形成三层并发控制，容易死锁。

**建议:** 统一并发控制层：
- `_doc_executor` → 提升到 `max_workers=6`（或环境变量配置）
- 去 Semaphore，用线程池自身的队列做排队
- 或者 Semaphore 在外层控制提交速率，线程池在内层执行

---

### ⚠️ 冲突7: `kb_id` 在 `ingest_job()` 中的传递链断裂

**当前代码** (`routes.py` 第 920 行):
```python
result = subprocess.run(
    [mineru_python, str(RAG_INGEST_SCRIPT), str(output_path), job_id],
    ...
)
```

**06 方案改造为:**
```python
kb_id = job.get("kb_id", "default")
result = subprocess.run(
    [mineru_python, str(RAG_INGEST_SCRIPT), str(output_path), job_id, kb_id],
    ...
)
```

**但还有第 1053 行的 `ingest_batch()` 也需要改:**
```python
# routes.py 第 1052 行，ingest_batch 函数中
result = subprocess.run(
    [mineru_python, str(RAG_INGEST_SCRIPT), str(output_path), job_id],
    ...
)
```

**问题:** 方案只说了一个调用点，实际有两个。而且 `rag_ingest.py` 的 `ingest()` 函数需要修改签名——当前签名是 `ingest(file_path, source_id=None)`，需要改为 `ingest(file_path, source_id=None, kb_id="default")`。

### ⚠️ 冲突8: 同一文件换知识库时的删除逻辑问题

**当前 `rag_ingest.py` 第 206 行:**
```python
cur.execute("DELETE FROM parent_child_db_1024 WHERE c_metadata->>'source' = %s", (source_id,))
```

**问题:** 假设文件 A 先在 KB-预算 入库 (`source=a1`, `kb_id=kb_budget`)，后来用户把它迁移到 KB-国库 (`kb_id=kb_treasury`)，重新入库时 source 还是 `a1`。

DELETE 语句只按 `source` 匹配，会删掉 KB-预算 和 KB-国库 中所有 `source=a1` 的切片。如果之前有两个 KB 里都有这个文件的切片，就全丢了。

**建议:** DELETE 改为 `WHERE c_metadata->>'source' = %s AND c_metadata->>'kb_id' = %s`。

## 三、批量上传的实际可行性问题

### ⚠️ 问题9: HTTP 上传 500 个文件不可行

**现实约束:**
- 浏览器 multipart/form-data 上传 500 个 PDF（假设每个 10MB = 5GB），HTTP 请求必然超时
- FastAPI / Nginx 默认 body 大小限制通常 < 100MB
- 前端浏览器标签页会因内存耗尽崩溃

**06 方案的三个入口中:**
1. `[拖拽文件夹]` + `[批量选择文件]`：这两个走浏览器的 `<input type="file" multiple>`，如果不做分块上传，500 个文件不可能。
2. `[扫描服务器目录]`：这个是可行的——文件已经在服务器上，只需要发目录路径。

**建议:** 明确三种上传方式的实现策略：
- **少量文件 (< 20个)**: 浏览器直接上传（保留现有 upload 路由，放开3个限制到20个）
- **大量文件 (20-500个)**: 要求用户先把文件放到服务器目录，用"扫描服务器目录"方式导入
- **API 层面**: `/file-parse/batch` 接受的是"文件路径列表"而非上传文件流

---

### ⚠️ 问题10: 分配预览 (preview-allocation) 的文件来源不清

**方案设计:**
```
步骤1: 选择文件 → 步骤2: 自动分配预览
```

**问题:** 步骤2 调用 `POST /file-parse/preview-allocation` 时，文件列表从哪来？
- 如果是浏览器上传：文件还没传到服务器，preview-allocation 只能拿到文件名列表
- 如果是目录扫描：服务器已经可以遍历目录拿到文件列表

**目前方案中 `preview-allocation` 收到的 body 是 `{files: [{filename: "..."}]}`，只能根据文件名匹配**，这是合理的但需要标注清楚边界。

**建议:** 明确 preview-allocation 只依赖 `filename` + `dirname`，不需要文件内容。

---

### ⚠️ 问题11: 目录扫描的第二级自动映射到知识库缺少实现细节

**方案第六章:**
> "二级子目录名 → 走知识库名称匹配 → 匹配成功则设为 kb_id"

**问题:** `knowledge_bases` 表中的 `name` 是动态数据（"预算管理"、"国库支付" 等），而目录名也是动态的。两者之间的匹配规则是什么？

- 精确匹配？`dirname == kb.name`
- 包含匹配？`dirname in kb.name` or `kb.name in dirname`
- 需要另外建一个 `directory_to_kb` 映射表？

**建议:** 方案需要明确匹配逻辑。最简方案：在 `knowledge_bases` 表加 `directory_keywords` 字段（JSON 数组），如 `["预算", "budget"]`，目录名包含任意关键词即匹配。

## 四、数据库设计问题

### ⚠️ 问题12: c_metadata 分批迁移的 ctid 有风险

**06 方案迁移 SQL:**
```sql
WHERE ctid IN (
    SELECT ctid FROM parent_child_db_1024
    WHERE c_metadata->>'kb_id' IS NULL
    LIMIT 500
)
```

**问题:** PostgreSQL 的 `ctid` 是一个物理行标识符，当行被 UPDATE 后 `ctid` 会改变。虽然这里每次只 UPDATE 500 行且 COMMIT 后才取下批，所以不会跑偏。但更安全的做法是用主键或 `source` 字段去重：
```sql
UPDATE parent_child_db_1024
SET c_metadata = c_metadata || jsonb_build_object('kb_id', 'default', 'enabled', true, 'tags', '[]'::jsonb)
WHERE c_metadata->>'kb_id' IS NULL
AND c_metadata->>'source' IN (
    SELECT c_metadata->>'source' FROM parent_child_db_1024
    WHERE c_metadata->>'kb_id' IS NULL
    LIMIT 500
)
```

**严重度:** 低。实际可以工作，但不够规范。

## 五、前端设计差距

### ⚠️ 问题14: 方案缺少 `region_code` 编码体系说明

06 方案使用了 `1301000`（7位）和 `130000000`（9位）两种编码，但没有说明为什么有两种长度。真实达梦数据库 `RDYS_BAS_MOFDIV` 中市级 (`LEVEL_NO=2`) 的编码有 7 位和 9 位两种。

**现有 `routes.py` 第 518 行已经做了适配:**
```python
if len(r[0]) == 9 and r[0].endswith('000'):
    name_map[r[0][:7]] = r[1]  # 9位→7位映射
```

**建议:** 在方案的匹配引擎部分注明：`region_code` 统一用达梦数据库原始值（可能是7位或9位），匹配引擎不负责编码转换。

---

### ⚠️ 问题15: 方案中 KB 选择器的 "文档数/切片数" 统计在跨 KB 查询时怎么算

**方案第5.1节:**
> "选中后重新请求 loadKnowledgeBase(kb_id)，统计卡片也随之刷新"

**问题:** `GET /ragdata/knowledge` 加 `?kb_id=` 过滤后，返回的 `total_files` 和 `total_chunks` 是该 KB 的统计。但前端上方 4 个指标卡片（文档资产、向量切片、处理中、已完成）中，"处理中"和"已完成"来自 job 列表而非 knowledge 查询。

选中不同 KB 后，job 列表的统计是否需要跟着刷新？job 本身没有 `kb_id`——除非改造 state_manager 在 create_job 时写入 `kb_id`。

**建议:** Phase B 改造 state_manager 时给 job 加上 `kb_id` 字段，前端统计卡片根据 `selectedKbId` 过滤 job 列表。

## 六、与真实需求的差距

### ❌ 差距16: 方案没有详细说明"标签"的作用

**用户可能期望:** 标签应该可以在检索时过滤/加权，在知识库浏览时做分组筛选。

**建议:** 方案中增加说明：Phase E 标签仅做存储和展示，检索过滤在后续版本实现。

### ❌ 差距17: 缺少中文化默认数据

**方案 Section 3.4:** 内置规则只列了 3 个城市 + 省本级，写了 `-- ... 其余 8 地市` 省略。

**建议:** 补充完整 12 地市的迁移 SQL。达梦数据库 `RDYS_BAS_MOFDIV` 中 `LEVEL_NO=2 AND MOF_DIV_CODE LIKE '13%'` 查出来的是标准数据源，迁移脚本应该与之一致。

---

### ❌ 差距18: P0 计划有"停止/暂停"功能，06方案只做了取消

**P0 计划 Phase 3 Task 10 用户流程:**
```
[查看失败(3)] [暂停] [取消]
```

**06 方案 API:** 只有 `cancel` 和 `retry-failed`，没有 `pause/resume`。

**评估:** 暂停功能在千量级场景中很重要——几个小时的处理过程中可能需要暂停。但实现复杂（需要等当前正在处理的文件完成后停止调度）。

**建议:** 在方案中标注 `pause` 为 P2（后续迭代），先做 `cancel` + `retry-failed`。
