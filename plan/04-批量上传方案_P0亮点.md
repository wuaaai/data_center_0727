## 一、场景分析

### 1.1 现有内网服务接口

内网已暴露 Maas 平台的文档解析服务：

```bash
curl -X POST "https://910b.hbmaas.com/idp-model-1000000232-9093/file_parse" \
  -H "Content-Type: multipart/form-data" \
  -F "files=@./xxx.pdf" \
  -F "format=markdown"
```

**接口特点：**
- 同步阻塞式：提交文件后等待解析完成再返回
- 不支持进度条（一次性返回结果）
- 格式单一：`format=markdown`，返回 Markdown 格式文本
- 无任务管理：没有队列、没有状态查询、没有取消

### 1.2 我们系统的当前状态

当前有两个解析入口：
- `POST /api/parse` (端口 8003) — 异步提交 + 任务队列 + SSE 进度推送
- `POST /ragdata/upload` (端口 8001) — 前端上传 → 代理调用 8003 的 `/api/parse`

**问题：** 与内网 Maas 接口协议不统一，未来如果切换解析引擎，需要大量改代码。

### 1.3 核心设计决策

**我们的接口要与内网 Maas 保持一致，同时扩展异步任务能力。**

Maas 接口的核心协议：
```
POST /file_parse
  files=@xxx.pdf         # multipart 文件上传
  format=markdown        # 输出格式
  → 同步返回 Markdown 文本
```

我们基于此协议扩展，增加异步模式：
```
POST /file_parse
  files=@xxx.pdf         # multipart 文件上传
  format=markdown        # 输出格式
  mode=async             # 🆕 sync(默认) | async
  kb_id=xxx              # 🆕 可选：目标知识库
  region_code=1301000    # 🆕 可选：地区编码
  tags=预算,2026          # 🆕 可选：标签
  → sync: 同步返回 Markdown
  → async: 返回 task_id，后续通过 GET /file_parse/{task_id} 查询
```

## 二、接口设计（兼容内网 Maas）

### 2.1 统一文件解析接口

#### POST /file_parse — 核心接口

**请求（与 Maas 兼容）：**

```bash
# 同步模式（与 Maas 完全一致）
curl -X POST "http://127.0.0.1:8001/file_parse" \
  -F "files=@xxx.pdf" \
  -F "format=markdown"

# 异步模式（我们扩展）
curl -X POST "http://127.0.0.1:8001/file_parse" \
  -F "files=@xxx.pdf" \
  -F "format=markdown" \
  -F "mode=async"
```

**参数说明：**

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `files` | file(s) | ✅ | PDF/DOCX/DOC 文件，支持多文件 |
| `format` | string | ✅ | 输出格式：`markdown` \| `docx` \| `json` |
| `mode` | string | ❌ | `sync`(默认) \| `async` |
| `kb_id` | string | ❌ | 目标知识库 ID（async 模式） |
| `region_code` | string | ❌ | 地区编码（async 模式自动入库时使用） |
| `tags` | string | ❌ | 标签，逗号分隔（async 模式） |

**响应 — sync 模式：**

```json
{
  "code": 200,
  "data": {
    "filename": "xxx.pdf",
    "format": "markdown",
    "content": "# 第一章 总则\n\n...",
    "page_count": 20,
    "parse_time_ms": 45230
  }
}
```

**响应 — async 模式（单文件）：**

```json
{
  "code": 200,
  "data": {
    "task_id": "a1b2c3d4e5f6",
    "status": "queued",
    "filename": "xxx.pdf"
  }
}
```

**响应 — async 模式（多文件，返回批量任务）：**

```json
{
  "code": 200,
  "data": {
    "batch_id": "batch_a1b2c3",
    "tasks": [
      {"task_id": "a1b2c3d4e5f6", "status": "queued", "filename": "xxx.pdf"},
      {"task_id": "b2c3d4e5f6a1", "status": "queued", "filename": "yyy.pdf"}
    ],
    "total": 2
  }
}
```

## 三、解析引擎抽象层（可插拔）

### 3.1 设计思路

将"调用哪个解析服务"抽象为一个可配置的 Adapter，未来切换引擎只需改配置。

```
┌──────────────────────────────────────────────┐
│              POST /file_parse                 │
│                   │                           │
│                   ▼                           │
│         ┌───────────────┐                    │
│         │  ParseRouter   │  根据配置选择引擎    │
│         └───────┬───────┘                    │
│                 │                             │
│     ┌───────────┼───────────┐                │
│     ▼           ▼           ▼                │
│ ┌────────┐ ┌────────┐ ┌────────────┐        │
│ │ Local  │ │ Maas   │ │ Custom     │        │
│ │ MinerU │ │ HTTP   │ │ Adapter    │        │
│ │ 8003   │ │ 内网    │ │ ...        │        │
│ └────────┘ └────────┘ └────────────┘        │
└──────────────────────────────────────────────┘
```

### 3.2 Adapter 接口定义

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class ParseResult:
    task_id: str
    status: str  # queued | processing | completed | failed
    progress: str
    progress_pct: int
    content: str | None = None      # sync 模式返回的文本
    output_path: str | None = None  # async 模式返回的文件路径
    error: str | None = None

class ParseAdapter(ABC):
    """文件解析适配器抽象基类"""

    @abstractmethod
    def parse_sync(self, file_path, format="markdown") -> ParseResult:
        """同步解析：返回解析后的文本"""
        ...

    @abstractmethod
    def parse_async_submit(self, file_path, output_dir, format="markdown") -> str:
        """异步提交：返回 task_id"""
        ...

    @abstractmethod
    def parse_async_query(self, task_id) -> ParseResult:
        """异步查询：返回任务状态和结果"""
        ...

    @abstractmethod
    def parse_async_cancel(self, task_id) -> bool:
        """取消异步任务"""
        ...
```

### 3.3 内置适配器

#### LocalMinerUAdapter — 本地 MinerU 引擎（默认）

```python
class LocalMinerUAdapter(ParseAdapter):
    """调用本地 mineru_app 模型服务 (8003)"""

    def parse_sync(self, file_path, format="markdown"):
        # 提交到本地 pipeline 并等待完成
        from pipeline import process_single_file
        result_path = process_single_file(file_path, ...)
        return ParseResult(content=_read_markdown(result_path), ...)

    def parse_async_submit(self, file_path, output_dir, format="markdown"):
        # 提交到 model_manager 队列
        task_id = model_manager.submit(file_path, output_dir)
        return task_id
```

#### MaasAdapter — 内网 Maas HTTP 适配器

```python
class MaasAdapter(ParseAdapter):
    """通过 HTTP 调用内网 Maas 平台的 file_parse 接口"""

    def __init__(self, base_url=None):
        self.base_url = os.getenv("MAAS_PARSE_URL",
            "https://910b.hbmaas.com/idp-model-1000000232-9093")

    def parse_sync(self, file_path, format="markdown"):
        with open(file_path, "rb") as f:
            resp = requests.post(
                f"{self.base_url}/file_parse",
                files={"files": f},
                data={"format": format},
                timeout=300
            )
        data = resp.json()
        return ParseResult(content=data["data"]["content"], ...)

    def parse_async_submit(self, file_path, output_dir, format="markdown"):
        # Maas 不支持异步, 用线程池后台调 sync
        # 或者直接返回 NotImplemented
        raise NotImplementedError("Maas 不支持异步模式")
```

### 3.4 配置切换

```bash
# .env 或环境变量
PARSE_ENGINE=local          # local | maas | custom
MAAS_PARSE_URL=https://910b.hbmaas.com/idp-model-1000000232-9093
```

```python
# 引擎选择逻辑
def get_parse_adapter() -> ParseAdapter:
    engine = os.getenv("PARSE_ENGINE", "local")
    if engine == "maas":
        return MaasAdapter()
    elif engine == "local":
```

## 四、批量上传 & 批量处理方案

### 4.1 千文档场景的核心挑战

| 阶段 | 当前瓶颈 | 千文档耗时 | 优化方向 |
|------|---------|-----------|---------|
| 上传 | 最多 3 个/次 | 333 次请求 | 批量上传 + 目录扫描 |
| 解析 | 2 并发 worker | ~40 小时 | 动态扩缩 2→8 worker |
| 入库 | 全局锁 + 逐条 Embedding | ~42 小时 | 批量 Embedding + COPY |
| 前端 | 无批量进度 | 无法感知 | 批量进度面板 + SSE |

### 4.2 三种批量上传方式

| 方式 | 描述 | 适用场景 |
|------|------|---------|
| 📁 文件夹拖拽 | 拖拽整个文件夹到上传区域 | 文件已分类在本地文件夹 |
| 📎 批量选择 | Ctrl/Cmd + A 多选 | 文件分散在同一目录 |
| 🖥 服务器目录扫描 | 输入服务器本地路径 | 文件已在服务器磁盘上 |

### 4.3 服务器目录扫描 ⭐

**适用场景：** 1000+ 个 PDF 已经在服务器上（如 `D:\待处理文档\`），无需通过浏览器上传。

**流程：**
```
POST /file_parse/scan-directory
  {"path": "D:\\待处理文档\\", "recursive": true}
↓
返回目录结构 + 文件列表（含大小、类型）
↓
用户确认 → 选择目标知识库/标签映射规则
↓
POST /file_parse/import-directory
  {"path": "D:\\待处理文档\\", "kb_id": "kb_budget", "tags": ["预算"]}
↓
后台逐文件提交解析，全程 SSE 推送进度
```

**亮点：** 文件已经在服务器本地 → 跳过网络上传，直接本地读取 → 提交速度极快（每秒可达数十个文件）。

### 4.5 智能调度器 (Smart Scheduler)

#### 三级优先级

| 优先级 | 来源 | 行为 |
|--------|------|------|
| 🔴 高 | 前端实时上传 | 插队到队列头部，最多 2 个高优任务并发 |
| 🟡 中 | 批量导入任务 | 正常排队 |
| 🟢 低 | 失败重试 / 夜间任务 | 只有队列空闲时处理 |

#### 动态并发

```
Worker Count = min(
    MAX_WORKERS,                    # 配置上限
    max(1, floor(CPU_CORES * 0.5)), # CPU 自适应
    高优 +2, 低优 -1,                # 优先级调整
    积压 > 100 → +1                  # 积压调整
)

GPU 显存 > 80% → 不新增 worker
系统空闲内存 < 2GB → 降速
```

#### 失败重试

```
重试次数: 3 次
退避间隔: 1分钟 → 5分钟 → 15分钟
可重试: 网络超时 / API 限流
不可重试: 文件损坏 / 格式不支持
失败隔离: 不阻塞队列中后续文件
```

## 五、批量入库优化

### 5.1 优化对比

| 环节 | 当前 | 优化后 | 提升 |
|------|------|--------|------|
| DOCX 读取 | 单文件串行 | 并行 4 个 | 4x |
| Embedding API | 逐条 HTTP | 批量 32 条/次 | 32x |
| DB 写入 | 逐行 INSERT | COPY 批量导入 | 50x+ |
| 入库锁 | 全局互斥 | 知识库级锁 | N 倍 |

### 5.2 批量 Embedding

```python
# 旧: 逐条发送 (N 次 HTTP 往返)
for text in texts:
    resp = requests.post(embed_api, json=[text])

# 新: 批量发送 (N/32 次 HTTP 往返)
BATCH_SIZE = 32
for i in range(0, len(texts), BATCH_SIZE):
    batch = texts[i:i + BATCH_SIZE]
    resp = requests.post(embed_api, json=batch)
```

### 5.3 COPY 批量写入

```python
# 旧: 逐条 INSERT (N 次 DB 往返)
for text, emb, meta in zip(texts, embeddings, metadatas):
    cur.execute("INSERT INTO ... VALUES (%s, %s, %s)", ...)

# 新: COPY 批量导入 (1 次 DB 往返)
buf = io.StringIO()
for text, emb, meta in zip(texts, embeddings, metadatas):
    buf.write(f"{text}\t{emb}\t{json.dumps(meta)}\n")
buf.seek(0)
cur.copy_from(buf, "parent_child_db_1024",
    columns=("c_document", "c_embedding", "c_metadata"))
```
